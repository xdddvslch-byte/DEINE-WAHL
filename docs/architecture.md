# Архітектура і логіка оцінювання

## Принцип

Код — програвач, сценарій — дані. Усе, що стосується змісту (тексти, розгалуження, бали, наслідки, норми, статус перевірки), лежить у `data/`. Рушій `app.js` не містить жодного тексту дилем.

```
data/stsenarii/*.json ─┐
data/pryklady/*.json ──┼─► validate.js ─► app.js (обкладинка → рішення → розбір)
data/normy.json ───────┤        ▲
data/schema/*.json ────┘        └── tools/build.mjs ─► data/bundle.js   (офлайн / Electron / SCORM)
                                                    ─► docs/stsenarii.md (карта рішень)
                                                    ─► dist/strict/      (для zibraty.py організаторів)
                                                    ─► dist/deine-wahl-scorm12.zip
```

## Формат сценарію: стартовий формат організаторів + одне розширення

Ми використовуємо формат організаторів без змін у жодному з його полів: вузли `V1…`, варіанти з `naslidky.odrazu/vidkladeni`, `baly`, `chomu_taki_baly`, `zvorotnyi_zviazok`, `normy`; на рівні сценарію — `tsinnosti_v_konflikti`, `normy` з `yak_zastosovuietsia`, `zastosovnist`, `porady`, `pytannia_dlia_obhovorennia`, `dzherelo_vypadku`, `perevirka_zmistu`, `shi`.

**Що ми додали і чому.** Одне необовʼязкове поле `podacha` на рівні сценарію і вузла:

| Поле | Навіщо |
|---|---|
| `podacha.zagolovok`, `knopka`, `ikonka`, `mistse`, `nomer` | Обкладинка справи: заголовок, кнопка старту, підпис |
| `vuzol.podacha.zagolovok`, `khto`, `replika` | Сцена як діалог: репліка персонажа великим курсивом. Емоційний контекст вибору без ігровізації (вимога UX) |
| `vuzol.podacha.inertsiia`, `inertsiia_tekst` | Режим тиску часу: що «стається само», коли користувач не встиг |
| `vuzol.podacha.rozdum` | Питання для рефлексії саме для цього маршруту |

**Сумісність в обидва боки:**

- Без `podacha` будь-який сценарій формату організаторів відтворюється: заголовок кроку — `zapytannia`, «інерція» — за явним правилом. Доказ — приклади S01–S05 у застосунку («Приклади організаторів»).
- `node tools/build.mjs` пише `dist/strict/` — наші сценарії без `podacha`. Їх приймає `zibraty.py` організаторів без жодної правки: «OK: сценаріїв 3, вузлів 26, варіантів 69».

## Перевірка (validate.js)

1. **Схема** — мінімальний валідатор JSON Schema, як у `zibraty.py`.
2. **Звʼязки** — ті самі правила, що в `zibraty.py`: вузли існують і досяжні, норми є в переліку й наведені в сценарії, одна роль користувача, 3–4 варіанти на старті, унікальні id.
3. **Наші додаткові:** немає циклів; у сценаріях команди щонайменше 3 послідовні етапи; попередження, якщо варіант кращий за інші за всіма трьома вимірами («очевидна» відповідь); попередження про норми зі статусом «не звірено»; перевірка `podacha.inertsiia`.

## Система оцінки

- **Три виміри:** доброчесність, ефективність, довіра (як у форматі організаторів).
- **Правило:** бал за вимір = сума балів обраних варіантів. Без ваг, ШІ чи випадковості.
- **Загального балу немає.** Розбір показує баланс трьох вимірів, внесок кожного рішення і пояснення «чому такі бали».
- **Пояснюваність:** конфлікт цінностей, зворотний звʼязок про рішення (не про людину), норми з цитатою й редакцією, застосовність норм, поради.

## Груповий режим

Ведучий проєктує сцену; аудиторія голосує руками або картками; ведучий фіксує кількість. Зберігаються лише лічильники в памʼяті вкладки — ні імен, ні пристроїв, ні мережі. Розподіл приховано до команди ведучого. У розборі видно рішення, де група розійшлася найбільше, і питання для обговорення.

## Офлайн і збереження

Працює з `file://`, в Electron, у SCORM-пакеті. Локально (`localStorage`) зберігається лише перелік id пройдених справ для позначки ✓. Вибори й бали не зберігаються.

|---|---|

| **Курси МОУ / ВВНЗ** | Набір сценаріїв під тему заняття; груповий режим для семінару; PDF розбору для конспекту |
